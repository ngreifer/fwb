### Seventh pass: simultaneous percentile bands

`simultaneous_ci_level(ci.type = "perc")` no longer searches for the adjusted level; it
computes it. `sup_t_entry_levels()` gives, for each bootstrap draw, the narrowest pointwise
level at which that draw enters the band, and the answer is the `ceiling(level * R)`th
smallest of those — two `rank()` calls per parameter and one partial sort, with no interval
ever constructed. `simultaneous_p_value()` reads the same entry levels the other way round.

The derivation is exact with respect to the package's own interval definition rather than an
approximation to it. For draw `r` and parameter `j`, the interval at level `l` is
`[norm_inter(t_j, p), norm_inter(t_j, 1 - p)]` with `p = (1 - l)/2`; `norm_inter()` returns
the `i`th order statistic exactly at `p = i/(R + 1)` (verified: max difference 0 over all
`i`), so the coordinate is inside exactly when `p <= min(i, R + 1 - i)/(R + 1)`. Checked
against a 20 001-point grid search per coordinate, and the entry-level coverage function is
*identical* to the interval-by-interval one — max difference exactly 0 over 400 levels.

The `bisect` and `optimize` searches were used to validate the exact computation and then
removed; only the exact method remains. The coverage function they shared moved to
`tests/testthat/helpers.R` as `simultaneous_coverage()`, so the tests still check the algebra
against the definition (build the intervals, count the draws) rather than restating the
shortcut. `test-summary.R` also brute-forces the answer over every achievable level at
`R = 120` and compares.

**Validity, over 160 cells** (R ∈ {99, 199, 550, 1001} × level ∈ .5–.99 × k = 2–6):

| | under-covers |
| --- | --- |
| exact (`supt`) | 0 of 160 |
| `bisect` | 0 of 160 |
| `optimize` | **89 of 160** |

The old objective was `R * |coverage - level| + l`, which takes whichever adjacent step is
*closer* to the target and, on a tie, the smaller level. Both land below nominal, and for a
confidence band that is the wrong side to err on.

**Efficiency** (measured before the searches were removed):

| | 75 level×k calls | 20 × 6 p-values | R = 20 000, k = 5 |
| --- | --- | --- | --- |
| exact | 0.045 s | 0.030 s | 0.027 s |
| `bisect` | 0.412 s | — | 0.058 s |
| `optimize` | 0.418 s | 1.265 s | — |

**Two things the exact route gets right that bisection did not.**

* It is not floored at `level`. Bisection searched `[level, Bonferroni]`, so it could never
  return a level below `level` — but when `ceiling(level * R) == R` the empirical coverage
  saturates at 1 and a *narrower* pointwise level suffices. At R = 99, level = .99, the
  exact answer is .98 (coverage 1.00) where bisection returned .99. Both valid; the exact
  one is narrower. This only arises when the requested level exceeds what R draws can
  resolve, and is worth remembering as a small-R artifact rather than a bug — a user asking
  for a .99 simultaneous band from 99 draws is asking for more resolution than they have.
* **The exact level needs a few-ulp nudge, which is not cosmetic.** At the exact level the
  binding draw sits *on* an endpoint, and `compute_ci()` receives the level rather than `p`
  and recomputes `p = (1 - level)/2`. Because the level is near 1, that round trip loses
  about an ulp of `p` — enough to flip `floor((R + 1) * p)` from `i` to `i - 1`, moving the
  endpoint a hair inside the binding draw and leaving coverage one draw short. It bit 2 of
  the first 30 cells before being handled. Adding `16 * .Machine$double.eps` to the level
  fixes it and moves the endpoints by ~1e-14, far below the data's own precision.

Still open as a possible refinement: `norm_inter()`'s knife-edge at integer `(R + 1) * alpha`
is the underlying fragility, and it would be more robust for `compute_ci()` to accept the
tail probability directly rather than reconstructing it from the level. Not needed for
correctness now that the nudge is in place.

### The architecture change

`fwb()` and `vcovFWB()` no longer *replay* the random number stream to recover the weights; they **record** it. Before any work is dispatched, `make_stream_seeds(R)` derives `R` independent L'Ecuyer-CMRG streams (via `parallel::nextRNGStream()`) from one draw off the caller's stream, and each replicate seeds its own weight draw from its own stream.

What that bought, all verified:

- The replicates depend on the seed and nothing else — not `cl`, the worker count, `verbose`, the caller's `RNGkind()`, or randomness in `statistic`. Checked across 8 backend configurations × 6 weight types × both `simple` settings × cluster/strata combinations.
- A plain `set.seed()` suffices; `set.seed(n, "L'Ecuyer-CMRG")` is no longer needed and `parallel::clusterSetRNGStream()` no longer has any effect.
- `fwb.array()` needs no backend, no RNG setup, and no `pblapply()`; it works after `stopCluster()` and after `saveRDS()`/`readRDS()`.
- BCa intervals work in every case, including `simple = TRUE` with a random `statistic`.
- `vcovFWB()` still equals `fwb(simple = TRUE)` + `vcov()` for all 6 weight types on `lm` and `glm`, and is itself backend-invariant.
- `wtype = "multinom"` with `simple = FALSE` still matches `boot::boot()`, with and without strata.

Version bumped to 0.7.0; `parallel` moved to `Imports`.

### Three consequences worth knowing

1.  **`simple = TRUE` and `simple = FALSE` no longer agree.** `simple = FALSE` keeps its single batch draw (that is what preserves *boot* parity); `simple = TRUE` draws per replicate from recorded streams. They consume the stream differently. Before 0.7.0 they coincided for the continuous weight types, and `test-fwb.R` asserted it — that assertion is now inverted, with a comment. Both settings remain reproducible and both draw from the same weight distribution (checked: same mean and variance to 1%).
2.  **`parallel::clusterSetRNGStream()` is now a no-op for `fwb()`.** `vignette("fwb-rep")` Case 5 currently tells users to use it instead of `set.seed()`; that advice is now wrong, not merely unnecessary. Folded into §5.
3.  **A pre-existing `waldo` bug is now reachable.** `waldo::compare()` on two *differing* large-magnitude integer vectors with a numeric `tolerance` overflows in its own diff and errors with `missing value where TRUE/FALSE needed`. `<fwb>` objects have always carried a `seed`, but two objects from the same `set.seed()` used to have identical seeds, so waldo short-circuited. Now that two runs can legitimately differ, `expect_equal(f1, f2, tolerance = ...)` on whole objects hits it. Worth reporting upstream (`r-lib/waldo`); `boot` objects have the same exposure. Our own tests compare `$t` instead.

## 1. Open questions

### 1.1 `check_statistic()` is dead code — resolved, now called

Rewritten and wired into `fwb()`. Two checks, both conditional on one thing:

**A function with `...` is exempt from every check.** That is the whole design, not an escape hatch. `fwb()` calls `statistic(data, w, ...)`, so a function with `...` can accept whatever it is handed and nothing about its formals can be shown to be wrong. It is also what makes this safe for other packages: anything that wraps `statistic` has to forward arguments to the function it wraps, and therefore has `...`. Keying the exemption on `...` rather than on a list of known packages means *progressify*'s wrapper — and anything written later — passes without `fwb` knowing it exists. The earlier plan to test for "at least two named arguments" would have passed *progressify* only by luck, since its wrapper happens to have two named arguments after `...`; a wrapper written as `function(...)` alone would have failed.

Given no `...`:

1. At least two formals, since the data and the weights are supplied positionally and a one-argument function can never receive the weights.
2. No formal *after the first two* may share a name with one of `fwb()`'s own formals, because `fwb()` matches such a name first and the argument could never be supplied through `...`. The first two are excluded deliberately: they are positional, so `function(R, wtype)` is perfectly legal and works.

`test-input-guards.R` covers all of it, including the *progressify*-shaped wrapper and the legal-collision case.

### 1.3 `vcovFWB()`'s fast `lm` path mishandled a rank-deficient replicate — fixed

Found while testing the exhaustive multinomial change, and worse on inspection than first described.

`.lm.fit()` is the raw decomposition. Unlike `lm.fit()`, it leaves the coefficients in **pivoted order** and leaves the aliased ones at whatever the decomposition produced, typically 0. The fast `lm` path used the result as-is, so a replicate whose weights left the design rank-deficient did two wrong things at once:

1. **An aliased coefficient came back as 0, not `NA`**, so `use = "pairwise.complete.obs"` could not drop it and a replicate that estimated nothing was averaged in as though it had.
2. **Worse: coefficients could be reported against the wrong parameter.** `dqrdc2` moves negligible columns to the end, so with three columns and the second aliased the pivot is `1 3 2` and the third column's estimate lands in the second column's slot.

The second is the serious one, and it is easy to reach — a dummy that is 1 for a single unit becomes an all-zero column in any resample that drops that unit, and the reordering bites whenever it is not the last column. With `y ~ x2 + x1` where `x2` is such a dummy, **125 of 400 replicates** were affected:

| | (Intercept) | `x2` | `x1` |
|----|----|----|----|
| old | 2.661 | 1.970 | 0.732 |
| fixed | 2.661 | **2.248** | **0.630** |
| `lm()` | 2.661 | 2.248 | 0.630 |

12% understated on `x2`, 16% overstated on `x1`.

Fixed by mirroring `lm.fit()`: mark the trailing pivoted positions `NA`, then restore the original column order. `glm` models were never affected (`glm.fit()` un-pivots and sets `NA` itself), nor was the general `update()` path, nor `fwb()`. Verified that `vcovFWB()` now agrees with `fwb(simple = TRUE)` exactly on designs with rank-deficient replicates for `"exp"`, `"multinom"`, and `"poisson"`, and that the exhaustive `n = 4` case matches `fwb()` to the digit. `test-vcovFWB-internals.R` covers both halves, and asserts that the situation actually arises in its sample of weights before asserting anything about it.

### 1.5 Exhaustive multinomial sampling breaks `boot` parity at very small `n`

Implemented at your request, and worth recording against the standing constraint that `wtype = "multinom"` match `boot::boot(., stype = "f")`.

`boot` always samples. Enumerating instead means the two disagree whenever `R` reaches the number of distinct resamples — `n^n` without strata, `prod_s n_s^{n_s}` with them, computed over clusters when clustered. With the default `R = 999` that is `n <= 4`; `n = 6` already has 46656 resamples. Every `boot` parity test in the suite uses `n` of 60, 300, or 2000, so none is affected, and `test-wtypes.R` now checks parity at 60 and 300 explicitly.

The divergence is in fwb's favour: enumeration gives the exact bootstrap distribution rather than a sample from it, with each weight vector appearing as often as its multinomial coefficient requires (at `n = 3`: once for `(3,0,0)`, three times for `(2,1,0)`, six times for `(1,1,1)`). Estimates also stop depending on the seed. But it is a real departure from `boot`, and `?fwb` says so in the `"multinom"` entry.

## 2. Performance

Ordered by expected payoff.

1.  **`empinf.reg()`** — **measured; leaving as is.**

    The premise held: `.lm.fit()` on the `R × n` design matrix really is the dominant cost. At `n = 1000, R = 5000` it takes 2.0 s against 0.17 s for `fwb.array()` and 1.8 s for the `fwb()` run that produced the object — so computing the influence values costs more than drawing the bootstrap.

    The proposed fix does not deliver, because the answer depends entirely on which BLAS R is linked against. `.lm.fit()` calls LINPACK `dqrdc2`, which is level-1 BLAS and so indifferent to the library; `crossprod()` calls `dsyrk`, which is level-3 and is *not*.

    | | reference BLAS | Accelerate |
    |----|----|----|
    | `.lm.fit()` (current) | 2.04 s | 0.52 s |
    | `qr(LAPACK = TRUE)` | 2.60 s | 0.27 s |
    | `crossprod()` + `chol()` | 2.13 s | 0.02 s |

    (`n = 1000, R = 5000`; the pattern is the same at every size tested from `n = 200` up.)

    Under the reference BLAS that CRAN's macOS and Windows builds ship — what most users have — the normal equations are no faster, and up to 1.7× *slower* in the `R ≈ n` corner. Under an optimized BLAS they are 30×. Switching would optimize for the minority configuration and mildly pessimize the majority.

    Accuracy is a second, smaller strike. Judged against an SVD reference, relative error in `L`:

    | | `n=200, R=1000` | `n=1000, R=1001` | `n=2000, R=2001` |
    |----|----|----|----|
    | `.lm.fit()` | 2e-14 | 1e-13 | 1e-11 |
    | `crossprod()` | 9e-14 | 1e-08 | 4e-06 |

    `cond(X'X)` reaches 1e12 at `n = 2000, R = n + 1`, which is legal — `check_ci_feasible()` only requires `R > n`. `chol()` did not fail anywhere tested, but there is a hard-failure mode there that QR does not have. In fairness this loss is immaterial for the use: `L` only feeds `a = ∑L³ / 6(∑L²)^1.5`, where the errors are relative and largely cancel — `a` agreed to 7 significant digits and the endpoints to every digit printed. So the accuracy argument alone would not decide it; the timing does.

    Centering the matrix first, as originally suggested, is sound and worth recording. Because `rowSums(X) == 1` exactly, the column-centered `Xc` satisfies `Xc %*% 1 == 0`, so `crossprod(Xc)` is singular with null vector `1`; adding `λ11'` makes it positive definite without moving the solution off the complement of `1`, and pins it to the sum-zero solution — which is exactly the centered coefficient vector wanted, so the explicit centering step disappears. It buys about half a digit of accuracy and costs an `R × n` copy. Not enough to change the verdict.

    `qr(LAPACK = TRUE)` (blocked `dgeqp3`) is the interesting middle: full QR accuracy, 2–3.5× faster than `.lm.fit()` under an optimized BLAS. But it is 25% slower under the reference BLAS, so it has the same shape of problem. Worth revisiting only if R's default BLAS changes.

2.  **`"multinom"` weight generation** — **done**, as `tabulate_rows()` in `R/utils.R`.

    The offset-`tabulate()` idea works, but only for small `n`, and the reason is not the one I assumed. It is not about the bin array fitting in cache — it still wins at `n = 100, R = 50000`, five million bins. It is about per-row overhead, which is most of the work when `n` is small and negligible when it is large. Measured against `t(apply(i, 1L, tabulate, n))`, tabulation only:

    | | `n=20` | `n=64` | `n=256` | `n=500` | `n=5000` |
    |----|----|----|----|----|----|
    | one offset `tabulate()` | **7.0x** | **2.7x** | **1.3x** | 0.9x | 0.6x |
    | `vapply()` over a transpose | 1.0x | 0.9x | 1.1x | **1.4x** | **1.5x** |

    Crossover is near `n = 384`; the implementation switches at 256, which is conservative and a round number rather than one fitted to this machine. The penalty for being on the wrong side near the boundary is ~10%.

    End-to-end on the whole generator the gain is smaller — 2.0x at `n = 20`, 1.15x at `n = 1000`, 1.08x at `n = 5000` — because `sample.int(n, n * R)` dominates at large `n` and cannot be touched without breaking parity. And generation is itself only part of a run: 1.3% of `fwb()` at `n = 100, R = 999`, rising to 19% at `n = 5000, R = 2000` (76% with a trivial statistic).

    Parity is preserved by construction: the counts depend only on the multiset of each row of the index matrix, never on the order within a row, and the index matrix is untouched. Verified identical output, and `test-wtypes.R` now checks `boot` parity at `n = 60` and `n = 300` — the existing parity tests all use the 2000-row fixture, so the small-`n` branch had no `boot` coverage at all.

    **Bug found and fixed along the way.** `t(apply(i, 1L, tabulate, n))` returned a `1 x R` matrix instead of `R x 1` when `n` is 1, because `apply()` simplifies a length-1 result to a vector. `fwb()` on a one-row dataset failed with "subscript out of bounds" for `"multinom"` and worked for every other `wtype`. Fixed as a side effect; `test-wtypes.R` has a regression test over all six types.

3.  **`capture.output()` in the general refit path** — **measured; leaving as is.**

    The wrapper costs 18.5 µs per call (a `textConnection()` alone is 8.6 µs of that). Measured end-to-end against a namespace copy with the call rewritten away, `n = 500`, `R = 500`, interleaved arms, median of 9:

    | fit | with | without | share |
    |----|----|----|----|
    | `coxph` | 0.615 s | 0.607 s | 1.3% |
    | `glm(y ~ w_std(x) + …)` | 0.336 s | 0.323 s | 3.9% |
    | `lm(y ~ w_std(x) + …)` | 0.158 s | 0.146 s | 7.6% |

    So the guess embedded in the original entry — that `coxph` is where this hurts — was backwards. A `coxph` refit is ~1.2 ms, which swamps 18.5 µs. The wrapper is proportionally worst on the *cheapest* models forced onto the general path, i.e. a plain `lm()` with a `w_*()` term, where the refit is ~0.3 ms.

    Even there the ceiling on the win is under 8%, and every alternative trades that for real risk:

    - A single `sink()` around the whole `applyfun()` recovers essentially all of it (indistinguishable from no wrapper at all in an isolated loop). But it swallows the progress bar when `verbose = TRUE`, and an error mid-loop leaks an open sink unless `on.exit()`-protected — a leaked sink makes the session look dead.
    - `withCallingHandlers(message = )` catches `message()` but not `cat()`/`print()`, which is the output `capture.output()` is there for. Not a substitute.
    - Hoisting one null connection out of the loop and `sink()`/`sink()`-ing per replicate would cut ~half, for the same leak risk.
    - Per-fitter quiet flags (`trace = FALSE` for `nnet::multinom()`) are free but narrow, and do not remove the need for the general wrapper.

    Worth recording: none of the three fits above emits *anything* on stdout during a weighted refit, so on the common cases this is pure insurance. That argues for keeping it — the cost is a few percent on the cheap end, and the models it exists for are exactly the ones nobody enumerated.

    (Watch for a measurement trap here: `capture.output({up <- refit()})` records nothing extra, but drop the assignment and it captures the auto-print of the returned model, which looks like 10 lines of fitter chatter. My first pass at "what does this emit" read 9–11 lines for all three fits for exactly that reason.)

### 2.4 `R CMD check` test warnings — fixed

The suite reported 131 warnings, 129 of them one message repeated: `'package:fwb' may not be available when loading`.

Not a package bug. It comes from base R's serializer (`OutEnvironment` in `serialize.c`), which warns whenever it serializes a reference to an *attached* package environment. `statistic` is serialized to every parallel worker along with its enclosing environment, and testthat sources `helpers.R` into an environment whose parent is `package:fwb` — so every worker in every backend test dragged that reference across and warned. Confirmed by reproducing it directly: a statistic whose enclosing environment's parent is `package:fwb` warns, and the identical function with `environment()` set to `globalenv()` does not. Note it is specifically the attached environment, not a namespace: a statistic defined inside a package does not warn.

Fixed in `helpers.R` by reparenting the four shared statistics to `globalenv()`. They use nothing but base and stats, and a user writing one at the top level of a script would get `globalenv()` anyway — so this also makes the tests reflect ordinary use rather than a testthat artifact.

The remaining two warnings were real and unrelated: `summary()` in a *progressify* test computed a BCa interval at `R = 80` with `n = 60`, landing on the extreme order statistics. `R` raised to 200 — the warning is fwb's own and is tested where it belongs, in `test-fwb-ci.R`.

### 2.5 Two tests failed under `R CMD check` but not `devtools::test()` — fixed

Reported by NG. `devtools::test()` was clean while `devtools::check()` gave two errors, both:

```
Error in `.check_ncores(cores)`: 3 simultaneous processes spawned
```

`--as-cran` sets `_R_CHECK_LIMIT_CORES_`, and `parallel:::.check_ncores()` then *errors* on a request for more than two processes — CRAN policy is a hard maximum of two. The backend tests asked for three in two places (`cl = 3` and a three-worker `multisession` plan), which is fine under `devtools::test()` and an error under check.

What makes this invisible from `devtools::test()` is the interaction of two environment variables:

- `--as-cran` sets `_R_CHECK_LIMIT_CORES_`, so three workers is an error.
- `devtools::check()` *also* sets `NOT_CRAN = "true"`, so `skip_on_cran()` does **not** skip. The tests carry `skip_on_cran()` and would be skipped on CRAN proper — so this would not have failed CRAN's own check, only every local `devtools::check()`.

Fixed with `max_test_workers()` in `helpers.R`, which returns 2 when the limit is in effect and 3 otherwise, mirroring `.check_ncores()`'s own condition (set unless literally `"false"`; `"warn"` still counts). Capping rather than skipping keeps the "results do not depend on the worker count" comparison running wherever a third worker is allowed and degrades it to two workers where one is not — two distinct counts are all the comparison needs. Labels are built from the value, so a failure never reports a worker count that was not used.

Worth remembering as a general point: **a clean `devtools::test()` is not evidence that `R CMD check` will pass.** The two differ in installed-vs-`load_all` name visibility (which is how the unqualified `.w_types()` slipped through earlier) and in check-only environment variables like this one.
